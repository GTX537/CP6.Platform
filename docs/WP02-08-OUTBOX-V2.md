# WP02-08 — PostgreSQL caller-transaction Outbox V2

`CP6.Platform.EntityFramework.OutboxV2` adds the opt-in `cp6-outbox-lease-v2` profile, version 1. The native `Cp6_OutboxMessage` remains the queue authority. This is a Platform library implementation; Main/CRM migration, host adoption, real broker delivery and original business acceptance are **NOT_RUN / UNPROVEN**.

## Owner adoption contract

The Owner supplies `IOutboxOwnerV2`, a trusted in-process adapter registered by the host, and the already resolved `ITrustedContextAccessorV1`. Request JSON, envelope tenant fields, a claimed worker ID or serialized proof cannot instantiate an authorized transaction. The adapter resolves the exact tenant/Owner/queue domain/route/worker and the approved publisher set, policy, schema, migration, mapping, complete writer set and cutover references. It reads current authorization and retention/handover evidence using the supplied `Context` and native `Transaction` only. It must not perform network I/O, commit, or create another transaction.

`OutboxRegistrationV2.AuthorityRows` is mandatory for write capabilities. These are the Owner's existing stable authorization, registration, policy and hold control rows, each with its exact schema/table/key. Every relevant Owner writer must update/lock that same durable fence; omission of an authorization dependency is an invalid host adoption. Outbox acquires the registered existing Owner advisory transaction locks, then these actual rows `FOR UPDATE`, then the unique RouteControl advisory lock and row, then stable native IDs, Binding rows and evidence. A Serializable snapshot may precede an advisory-lock wait: locking the actual changed authority row forces PostgreSQL `40001` rather than silently using a stale grant or hold. Merely sharing a mutex is insufficient. Hosts must supply the complete existing order and bounded fence list; missing rows, preheld unproven advisory locks, different connection/transaction, changed trusted context, wrong provider or unsupported isolation fail closed.

Write seams require an existing PostgreSQL Serializable transaction. Read recovery uses a separate ReadCommitted **READ ONLY** transaction and the current read/field grant, without requiring new-write authority. Store methods never begin, commit, roll back or dispose the caller's transaction. When an operation throws, the caller must roll back the entire unit of work. Only an explicitly definite PostgreSQL abort may be retried in a fresh transaction with the original IDs/input. Unknown commit is queried first; absence remains Unknown.

`AddPostgreSqlOutboxV2(model, schema)` is explicit model opt-in, not automatic migration. It preserves the native table, keys, global MessageId uniqueness, TenantId, payload bytes and hash domain. PostgreSQL `xmin` is the native/Binding/root token. The opaque ticket codec is `pg-xmin-v1:<uint>`; the legacy public `byte[] RowVersion` property uses the explicit four-byte network-order uint converter only in this opt-in model. Existing legacy models/contracts are unchanged. Actual adoption of this storage mapping, old rowversion columns, old in-flight rows and unknown history requires its own Owner migration/cutover; the library does not backfill missing ownership or epoch.

The Owner migration installs `OutboxPostgreSqlV2.GuardMigrationSql(schema)` after creating the opt-in model. Runtime never executes this DDL. Readiness checks exact EF tables/columns/token metadata and converter, actual unique indexes, and the native/Binding/DLQ and immutable-evidence triggers, including enabled event set, absence of WHEN/column filters, function body/language and fixed search path. Runtime DML roles must not own or alter the tables/functions/triggers, bypass trigger enforcement, or impersonate the migration role. The provided task fixture uses a distinct least-privilege runtime role. These guards enforce protocol correctness for adopted trusted writers; arbitrary SQL access is not a replacement for tenant authorization or database permissions.

## Claim and completion

1. Bind the caller's actual context/connection/transaction with `BindTransactionAsync`.
2. Call `ClaimBatchV2` with the original request ID and approved batch size. It persists native lease/attempt, Binding epoch/claim, the immutable batch input (including an empty result), per-native receipts and post-write tokens in the same transaction. A transaction-local token seal prevents subsequent native/Binding changes after the ticket was recorded.
3. Commit using the caller's actual database transaction. `PreparedClaimV2` cannot be published. In a new authoritative read transaction, `QueryClaimV2` compares the exact original input and returns `CommittedClaimTicketV2` only for visible committed receipts. There is no caller boolean that promotes a prepared ticket.
4. Before transport, `PrepareSendV2` rechecks the current ticket and approved time budget under the same root, and persists one send intent/mutation identity per claim. Commit this short transaction and release all locks before transport. `OutboxDispatcherV2` implements this sequence. A historical claim receipt or a repeated dispatch call does not authorize a second send. Send attempts survive uncertainty; unresolved intent is treated as `UNCERTAIN_DELIVERY`, never as proof of non-delivery.
5. `CompleteClaimV2` and `RenewClaimV2` compare the committed ticket, original input tuple, root phase/epoch, native/Binding versions, tenant/message/hash, current claim/owner/token/expiry and the database's current UTC clock. The final native update uses `clock_timestamp()` and strict `fence < expiry`; equality is expired. Expected versions are never replaced with current row values to repair an old ticket.

Publish confirmation transitions to Published. A definite transport failure uses the approved retry policy and persisted attempt count to decide RetryScheduled or DeadLettered; DLQ, native status, Binding, receipt and audit commit together. Renewal is Active-only, keeps message/claim/epoch/token/attempt, respects the total claim lifetime and yields new actual post-write versions. The old ticket stops working. Complete is allowed in Active or same-epoch Draining.

`PendingCommit` means writes have been prepared, not acknowledged. `QueryClaimMutationV2` uses the exact original mutation ID and canonical `MutationInput(...)`; identical reentry returns the original output with no extra state write, even after later epoch changes. A different tuple conflicts. `QueryRenewedTicketV2` confirms the exact renewal output. Gate rejections before state writes are distinct from `OutcomeUnknown`: after a real commit with lost response, every write may already be durable.

The dispatcher has separate transport and database outcome handling. Only `DefinitelyRejected` from a transport-specific adapter permits recording a publish failure. An ambiguous exception, timeout, cancellation after a possible send, or transport success followed by failed completion preserves the original identity and uncertainty. It never invokes legacy `MarkFailed`, retries with a replacement ticket/mutation, or claims network exactly-once. `PublishBudget` bounds the whole send-admission and transport window: a monotonic timer starts before the short validating transaction, and transaction waits, commit acknowledgement, disposal and message decoding consume that budget. The database clock remains the lease authority; the earlier monotonic start only shortens the window that its gate approved, without comparing worker UTC against the ticket. Exhausted budget or cancellation already signalled before transport prevents publisher invocation. The timeout uses only the remaining budget, retaining the original committed send-intent/mutation ID; it never creates a replacement ID to resend. A transport that ignores cancellation may still finish externally, which remains an uncertainty rather than a rollback claim. Original mutation recovery is read-only. The batch path uses a stable per-claim mutation identity and retains prepared claim input when a commit acknowledgement fails.

## Epoch and retention

`BeginDrainV2` persists Active → Draining with switch ID and expected control token. `AdvanceEpochV2` is a later transaction and requires that committed drain receipt, current epoch/control token, the bounded complete nonterminal inventory, no live claim, and authoritative Owner resolution of unknown transactions. Missing handover evidence persists Blocked without advancing. Pending and expired Dispatching rows move atomically with the root; expired claims append UNCERTAIN_DELIVERY history and retain original message/receipts. Terminal rows retain their historical epoch. No caller-supplied external epoch can replace this root.

`DeleteEligibleInTransactionV1` takes exact candidates and expected native versions. The Owner rechecks current policy/version, terminal Owner receipt, required-consumer set, reference closure, hold/unknown/conflict, dedup protection and verified archive under the same authority/root locks. Missing evidence retains the row or reports PolicyUnavailable. Eligible native/Binding/outbound DLQ deletion and RetentionAudit are one caller transaction. Immutable claim/mutation/send evidence and audit remain; payload absence means EVIDENCE_EXPIRED and cannot imply the business never ran. This seam does not erase InboxV1 original results or decide legal retention policy.

Legacy claim, Published/failure, requeue and retention exclude physically V2-bound native rows and related DLQ/Inbox identities. The database guard is the final protection for an old context without the opt-in model and for races; ordinary unbound V1 behavior stays available. Configure one dispatcher profile per route. A missing V2 root/model/guard is not permission to fall back to V1.
